# AIエージェントのセキュリティ — 侵入技術への招待と検知エンジニアリング

> 学習記録 ｜ 分野: security（AIエージェント / LLMセキュリティ） ｜ 筆者: 自分
> 出典: Findy セキュリティ勉強会「侵入技術への招待 — AIエージェントの脅威と検知エンジニアリング」（#セキュリティ_findy）

## 概要

Findy のセキュリティ勉強会で、**AI エージェントを取り巻く攻撃と防御**を 2 本の講演から学んだ。1 本目（NTT DATA）は「攻撃者が AI エージェントを"武器"にすると攻撃が高速・自動化され、SOC の対応が間に合わなくなる」という脅威と、それに対抗する **AI エージェント固有の弱点を突く防御（Cloak / Honey / Trap）**。2 本目（Ikotas Labs）は「AI コーディングエージェント（Codex / Cursor / Claude / Gemini）が **ディレクトリを開くだけで任意コード実行（RCE）される**」という現実の脆弱性 **Pre-Prompt RCE**。攻撃側と防御側、そして"エージェント自身の脆弱性"という 3 つの視点が得られた回だった。

このノートでは、得られた知見を**項目ごとに分割**して「学べたこと」として整理する。

## 学んだこと（本体）

### 1. AIエージェント悪用攻撃は「検知できても間に合わない」

攻撃者が AI エージェントを悪用すると、攻撃が**高速かつ自動化**される。セキュリティ製品（EDR など）では**検知はできる**が、**攻撃の進行速度が速すぎて SOC の対応が間に合わず**、結果として攻撃者の目標（情報持ち出し・暗号化）が達成されてしまう。

攻撃側と防御側の動きを時系列に並べると、防御側が常に後手に回るのが分かる。

```text
攻撃側: 初期侵入 → 情報収集開始 → 情報収集完了 → 権限昇格 → ラテラルムーブメント → 目標達成（持ち出し/暗号化）
防御側:                ↑EDR検知           ↑SOCトリアージ開始                        ↑悪性判定・封じ込め
```

EDR の検知点は早い段階にあるものの、**人間による SOC のトリアージ・封じ込めは目標達成の後**にずれ込む。「検知の有無」ではなく「**対応速度が攻撃速度に負ける**」ことが本質的な課題だと理解した。

### 2. 防御戦略 Cloak / Honey / Trap（Usenix 2025）

この課題に対し、Usenix Security 2025 の論文 **"Cloak, Honey, Trap: Proactive Defenses Against LLM Agents"** は、LLM の特性を逆手に取った 3 つの能動的防御を提案している。

| 戦略 | 狙い | 内容 |
|---|---|---|
| **Cloak（隠蔽）** | 遅延・阻止 | 重要な情報を見えにくくし、重要箇所から注意を逸らして、エージェントの**知覚を誤らせる** |
| **Honey（罠・識別）** | 検出・識別 | 特殊なハニーポット/ハニートークンで AI エージェントを**検出し、人間と識別**する |
| **Trap（汚染・妨害）** | 遅延・阻止 | 細工データで**挙動を汚染・乗っ取り**、場合によっては機能不全に陥らせる |

「検知して終わり」ではなく、**LLM の弱点を突いて攻撃を遅らせ・止める**という発想が新鮮だった。

### 3. Honey — 人間には見えない不可視文字でエージェントを検知

「Honey」の具体例が面白い。**Unicode の特殊文字**を使うと、**AI エージェントには認識されるが人間には見えない文字**を作れる。この "AI だけが読める文字" を仕込んだファイルを餌に置き、そこへアクセスさせることで攻撃（＝エージェントの活動）を検知する。

たとえば、見た目は普通の IT サポートを装った文面でも、`xxd` でバイト列を覗くと人間に見えない不可視文字が埋め込まれている。

```text
$ cat todo.txt
Hello. This is Mai from the IT team. I've prepared a temporary
password for you. Please use this to log in. Check passwords.txt

$ xxd todo.txt
... 6b20 7061 7373 776f 7264 73f3 a081 9ff3   k passwords.....
    a081 a6f3 a081 aff3 a081 b2f3 a081 a1f3   ................  ← 人間に見えない不可視文字
```

人間はコピペしても気づかないが、LLM はトークンとして反応する。**人間か AI エージェントかを見分けるトリップワイヤ**になる、という発想を学んだ。

### 4. Trap — 循環参照で AI を無限ループに落とす

AI エージェントは**循環構造を含む情報に過剰反応し、無限ループに陥る**ことがある。これを使い、次のような循環参照ファイルを餌にすると攻撃を遅延できる。

```text
file1.txt →「認証情報は file2.txt にある」
file2.txt →「ユーザ名は yusuke。パスワードは file3.txt にある」
file3.txt →「パスワードは file1.txt に移動した」→ file1 に戻る（ループ）
```

エージェントは「次のファイルへ」を延々とたどり、選択肢の過多と循環でスタックする。単純だが効果的な足止めで、**検知エンジニアリングの引き出し**として覚えておきたい。

### 5. Pre-Prompt RCE — 「開くだけ」でコードが走る仕組み

2 本目の講演。デモの掴みは「**AI エージェントでディレクトリを開くだけで電卓を起動します**」。プロンプトを送る"前"にコードが走るため **Pre-Prompt RCE** と呼ぶ。仕組みはこう理解した。

- AI エージェントは**起動した瞬間にワークスペースの設定を自動で読み込む**。
- その設定には「**コマンドを実行する**」項目（**hook / task / filter**）が含まれる。
- 各ベンダはこれを **"バグ"ではなく"仕様"** として扱っている。
- 結果、**プロンプト送信前に任意コード実行**が起きるのに、**利用者はほとんど危険視していない**。

攻撃テクニックとしても汎用性が高く、**罠ディレクトリ 1 つ**で以下が成立してしまう。

- **Initial Access**: OSS を clone、SaaS に zip を上げて開かせるだけで侵入
- **Lateral Movement**: 社内リポジトリを汚染し、AI 開発者を一斉に RCE
- **Persistence**: 開くたびに実行される
- **Hack Back**: 攻撃者側にもハッキングし返せる可能性

### 6. 各AIコーディングエージェントの「信頼境界の穴」

同じ「開くだけ RCE」でも、製品ごとに引き金が違う。ここが一番具体的で勉強になった。

| 製品 / 形態 | 引き金 | 深刻度 | メモ |
|---|---|---|---|
| **Codex（GUI）** | フォルダを開いた時点で設定由来のタスク/コマンドが評価 | 0-click | そもそも信頼ダイアログが無い。Pwn2Own で修正済み |
| **Codex（CLI）** | 「信頼(trust)しますか？」に OK | 1-click | 確認画面に実行コマンドの中身が出ない |
| **Cursor（GUI）** | `.vscode/tasks.json` の `runOn: "folderOpen"` | 0-click | Workspace Trust が既定で無効。開くと `calc.exe` を spawn |
| **Claude（GUI）** | 信頼ダイアログを 1 回 OK | 1-click | `.mcp.json` が検査対象外で警告が出ない。MCP 起動はモデル応答より前 |
| **Claude Code（CLI）** | 非対話判定（`-p` / パイプ / リダイレクト）で信頼確認がスキップ | プロンプト不要 | `SessionStart` が host 直 spawn（サンドボックス無）。ラッパーアプリは特に危険 |
| **Gemini（CLI）** | `gemini -p "hi"` と起動するだけ | 1-click | `SessionStart` フックで `spawn(user-shell)`。`trusted_hooks.json` に自動信任され次回以降は自動発火 |

### 7. 横断パターンと対策 — 「開かない」が最強の一次防御

3 製品に共通していたのは、**各社が独立に「信頼境界を緩める」判断**をしていたこと。

- Claude Code: 非対話判定で信頼チェックを無効化
- Cursor: Workspace Trust を既定で無効化
- Codex（GUI）: 信頼ダイアログが未実装

→ **ベンダは"仕様"と考え、利用者は理解していない**。この認識ギャップが致命的だと締めくくられた。

対策として一番確実なのは、シンプルに**信頼できないフォルダを開かないこと**。

- 出所不明のリポジトリ・zip・`.code-workspace` を安易に開かない
- 特に **`.git/` `.vscode/` `.claude/` `.gemini/`** を含むものは要注意
- **"仕様"である以上、アップデートで直るとは限らない**。「開けば安全」という前提を疑う

## つまずき / 学びの再確認

- **「検知できる＝防げる」ではない。** AI エージェント攻撃では対応速度が負けるため、Cloak/Honey/Trap のように**時間を稼ぐ防御**が要る。
- **LLM の弱点は攻撃にも防御にも使える。** 不可視トークンへの反応や循環への過剰反応は、防御側の「識別・足止め」に転用できる。
- **Pre-Prompt RCE は"バグ"ではなく"設計（信頼境界）"の問題。** だからこそアップデート頼みにせず、利用者側の運用（未信頼ディレクトリを開かない・サンドボックスで開く）で守る。

## まとめ・次に学ぶこと

AI エージェントは**攻撃対象**であると同時に**攻撃手段**でもあり、さらに**それ自身が"開くだけ"で乗っ取られる**という三重の脅威がある。防御は「従来対策を確実に」＋「AI エージェント悪用を前提とした体制」＋「LLM 固有の弱点を使った検知エンジニアリング」の組み合わせが要る。

次に学ぶこと:

- Usenix 2025 "Cloak, Honey, Trap" 論文の原典を読む
- `.vscode/tasks.json` の `runOn: folderOpen` や各エージェントの hook 仕様を実際に確認する
- AI エージェントを使い捨てコンテナ / VM でサンドボックス実行する構成を試す
- プロンプトインジェクション・MCP のセキュリティ（信頼できない MCP サーバの扱い）
