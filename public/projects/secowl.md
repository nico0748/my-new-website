
# 脆弱性調査支援アプリケーション「SecOwl」をつくってみた話

MBSD Cybersecurity Challenges 2026 に向けて作った、脆弱性診断の記録・報告ツールの話です。コンテストの診断では、調査から報告書まで最初から最後までこのアプリの上で進めました。ひと段落したので、なぜ作ったか、どう設計したかをまとめておきます。

## 1. システム概要

「SecOwl」は、Web アプリの脆弱性診断で行う **偵察・列挙 → 脆弱性調査 → トリアージ → 報告書** の一連の作業を、ローカルの **Markdown に 1 件 1 ファイル** で記録していく診断支援アプリです。

データベースは持たず、保存先のフォルダをそのまま Obsidian の保管庫として開けます。デスクトップ版（Electron）とブラウザ版があり、中身は同じローカルサーバーと画面です。さらに操作を **MCP サーバーとして公開** しているので、Claude から診断対象の作成から報告書の生成までを呼び出せます。

## 2. 作り始めた背景

### 2-1. チームの事情

コンテストのチームには、脆弱性診断が初めてのメンバーと経験者が混ざっていました。診断は手順の多い作業で、経験者は「まず攻撃面を洗い出して、入力点を棚卸しして、チェックリストを潰して……」と頭の中に流れが入っています。でも、それが本人の頭の中にしかないと、初めての人は **「次に何をすればいいか」が分からない**。

加えて、診断の記録まわりにもこんな問題がありました。

1. ツールの出力がターミナルに流れて消える
2. スクリーンショットがデスクトップに散らばる
3. 発見事項のメモの粒度が人によってバラバラ
4. 最後に報告書を書くとき、全部を集め直して手で表にする

### 2-2. 既存のやり方の限界

| 困りごと | これまで | SecOwl なら |
|---|---|---|
| 次に何をする？ | 経験者に聞く | フェーズの進み具合と「次の一手」を表示 |
| ツールの出力 | ターミナルに流れて消える | 実行ログとして自動で保存 |
| 証跡の画像 | デスクトップに散らばる | 発見事項ごとにまとめて、秘匿値は塗りつぶし |
| 深刻度の判定 | 人によってブレる | CVSS v3.1 計算機で決める |
| 報告書 | 最後に手で集め直す | 発見事項から表や章を自動で組み立て |

そこで、**経験者のやり方を「フェーズ」と「各フェーズで使うツールの手引き」としてアプリ側に形にする** ことにしました。

## 3. 診断の「型」をアプリに持たせる

### 3-1. E0〜E4 の 5 フェーズ

診断の流れを 5 つのフェーズに分け、それぞれに完了の条件を決めました。

| | フェーズ | 完了の条件 |
|---|---|---|
| E0 | 事前準備 | スコープと RoE に書面の承認がある |
| E1 | 偵察・列挙 | 攻撃面の一覧がそろい、入力点を洗い出した |
| E2 | 脆弱性調査 | チェックリストの全項目が「検出有」か「検出無」になった |
| E3 | 検証・トリアージ | 全発見事項に再現手順・証跡・CVSS・修正案がそろった |
| E4 | 報告 | 経営層と技術者の両方に向けて書き分けた報告書を納品した |

ホーム画面には、記録されたデータから判定した各フェーズの状態（未着手・進行中・完了）と「次の一手」が出ます。迷ったらそこを見れば、標準的な流れに沿って調査を進められる、というのが狙いです。

### 3-2. 各フェーズでできること

- **偵察**: nmap・httpx・nuclei・subfinder・ffuf などの出力を貼り付けると、形式を判定して攻撃面として取り込む。nuclei の自動検出は「下書き」として起票し、手で裏取りするまで報告書に載せない
- **調査**: OWASP WSTG v4.2 / Top 10:2025 に沿ったチェックリストと、ツールの実行ログを管理する
- **トリアージ**: 発見事項を個票として起票し、組み込みの CVSS v3.1 計算機でスコアと深刻度を決める。計算式は FIRST の仕様どおりに実装し、既知のベクタ 10 件で検算した
- **証跡**: スクリーンショットを発見事項ごとにまとめ、秘匿値を塗りつぶすマスキング機能と、Cookie・トークン・メールアドレスの伏せ字漏れの自動点検を備える
- **報告書**: 発見事項から報告書の表や章を自動で組み立て、HTML・印刷用 PDF・Word・Markdown で書き出せる
- **ツールの手引き**: 診断で使う 44 ツールの使いどころとコマンド例、7 つのユースケースを収録

### 3-3. Markdown 1 件 1 ファイルにした理由

診断対象を作ると、こんなフォルダができます。

```
<保存先>/<診断対象名>/
├── 00-診断対象/   スコープと RoE・進め方
├── 10-偵察/       攻撃面 1 件につき 1 ファイル
├── 20-調査/       チェックリスト・実行ログ
├── 30-トリアージ/  発見事項 1 件につき 1 ファイル
└── 40-報告/       診断報告書
```

1 件 1 ファイルにしておくと、Git で差分が見やすく、Obsidian からもそのまま読めて、Claude からも扱いやすい。アプリのフォームは frontmatter と本文の見出しに対応していて、保存するときは対象の項目だけを書き換え、アプリが知らない項目はそのまま残します。Obsidian で直接書き足しても壊れません。

## 4. 技術的な構成

| 領域 | 使っているもの |
|---|---|
| 画面 | React / Vite / デジタル庁デザインシステムのトークン |
| サーバー | Express（`127.0.0.1` のみ） |
| デスクトップ | Electron（GitHub Actions で macOS 用の .dmg を自動ビルド） |
| AI 連携 | MCP サーバー（stdio・39 ツール） |
| データ | Markdown（1 件 1 ファイル）+ JSON。DB は使わない |

Electron のメインプロセスが同じ Express サーバーを立ち上げて、その URL をウィンドウに読み込ませる構成なので、デスクトップ版とブラウザ版で画面のコードは 1 つだけです。チームメイトには .dmg を渡すだけで配れるようにしました。

## 5. 設計思想

### 5-1. 診断のデータを外に出さない

診断のデータは、それ自体が攻撃に使える情報の塊です。うっかり外に出ることがあってはいけません。

- サーバーは `127.0.0.1` だけで待ち受け、DNS rebinding 対策として Host・Origin・`Sec-Fetch-Site` を確かめる
- Markdown のプレビューでは生の HTML を描画せず、本文に書かれた **外部ドメインの画像も読み込まない**（診断中に外へ通信しない）
- ツールのアイコンもアプリに同梱し、実行中に外へ取りに行かない

### 5-2. 調査データだけを Git で共有する

アプリ本体と調査データを分けて、データのフォルダだけを別のリポジトリとしてチームで共有できるようにしました。同じ対象を複数人で調べても、全員が同じ一次情報を見ながら分担と裏取りを進められます。

### 5-3. 実行ランナーは「許可したものだけ」

デスクトップ版には、アプリから偵察ツールを実行するランナーがあります。便利な反面、診断ツールをアプリから叩けるのは危険でもあるので、かなり慎重に作りました。

- 実行できるのは許可したツールだけ（`curl` や `sudo` は無し）。シェルを通さず引数をそのまま渡す
- 実行前に、スコープ・書面の承認・診断期間と照らし合わせ、起動の直前にもう一度確認する
- 実行の記録は、各行に前の行のハッシュを持たせた **改ざん検知付きの監査ログ** に残す
- 他のユーザーが書き換えられる権限の実行ファイルは実行しない

「スコープ外を叩いてしまった」は診断で一番やってはいけないことなので、それを仕組みで防ぐことを優先しました。

### 5-4. 色だけに頼らない

配色はデジタル庁デザインシステムのトークンだけで組み、コントラストと色覚の違いによる見分けやすさを、トークンの生成時に自動で検査しています。基準を満たさなければ生成がその場で止まります。深刻度は色に加えて、区分名と形でも示すようにしました。

## 6. AI エージェントとの協働 — 人と Claude の役割分担

SecOwl の操作は MCP サーバーとして公開していて（39 ツール）、サーバーは保存先の Markdown を直接読み書きするので、アプリを起動していなくても動きます。

コンテストの診断では、こんな分担で進めました。

```
[Claude]  ← MCP 経由で SecOwl を操作
   │        攻撃面の登録・実行ログの記録・発見事項の起票
   ▼
[SecOwl]  ← すべてを Markdown で記録
   │
   ▼
[自分]    ← スコープの管理・結果の裏取り・深刻度の確定
```

ポイントは、**AI に任せる範囲と人が判断する範囲を、ツールの側で線引きした** ことです。サーバーからモデルには「自動検出をそのまま確定にしない」「証跡や本文に実際のトークンや個人情報を書かない」「報告書を読む前に最新の状態で組み立て直す」といった方針を渡しています。読み取りだけに絞って公開するモードも用意しました。

記録の粒度がそろっていて、報告書も確定した個票から機械的に組み立て直せるので、報告書・個票・証跡がそのまま追試の資料になる、というのも嬉しいところでした。

### 7-2. ハマったところ

- **`httpx` が別物だった**: macOS で `httpx` の実体が Python 版の httpx（pyenv の shim）になっていて、ProjectDiscovery 版のつもりで叩くと `No such option: -u` で落ちる。PD 版を入れて PATH で前に置く必要がありました
- **テストが自分の PC に左右される**: ツールの導入状況を点検する API のテストが、手元の本物の Homebrew や git の置き場所を見てしまい、環境によって結果が変わっていた。テスト側で環境を固定するように直しました
- **深刻度の色**: 「重要」を赤にしていたら「緊急」と見分けにくく、橙に変更。見た目を戻したり当て直したりで PR が何本か往復しました

## 8. さいごに

「経験者の頭の中にある手順を、初めての人でも追えるようにしたい」というところから始めたアプリでしたが、結果として、診断の流れそのものを設計し直すことになりました。

一番の収穫は、**ツールを作ることは、作業の「型」を言葉にすること** だという気付きでした。フェーズの完了条件を決めるには「何がそろえば次に進んでいいのか」を言語化する必要があり、AI に任せる範囲を決めるには「どこから先は人が責任を持つのか」を決める必要がありました。

まだまだ未完成ですが、次の診断でも使える道具として、引き続き育てていきます。ここまで読んでくださってありがとうございました。
