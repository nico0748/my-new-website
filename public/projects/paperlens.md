
# 論文読解支援アプリケーション「PaperLens」をつくってみた話

2 ヶ月。研究室の輪講で感じていたモヤモヤから作り始めた、論文を読むためのアプリの話です。別々に作っていた 2 つのアプリをひとつにまとめ直し、発表の場でも使える形になってきたので、なぜ作ったのか、どの機能がどの課題に効くのかを中心にまとめておきます。

## 1. システム概要

「PaperLens」は、論文 PDF を **1 文ごとの対訳** で読みながら、訳・用語・数式・読解メモを Markdown の保管庫（vault）に残していく、ローカルファーストな論文読解支援アプリです。輪講用に、**発表スライドと論文の根拠を線でつなぐ** 機能もあります。

![発表スライドと論文の対応の画面。スライドで囲んだ部分と、論文の根拠になる文や数式が色の線でつながっている](/projects/images/paperlens-slides.webp)
*発表スライドと論文の対応。スライドで囲んだ部分と、論文中の根拠の文・数式を同じ色の線でつなぐ*

できることをざっくり並べると、こんな感じです。

- **発表スライドと論文の対応**: スライドの一部を囲み、論文の文章・図・数式にリンクする
- **1 文ごとの対訳**: 論文を文単位に分け、PDF 上の位置と結び付けて、1 文ずつの日本語訳を並べる
- **用語・数式の記録**: 用語の説明と「この論文での使われ方」、数式の TeX と記号ごとの意味を残す
- **発表モード**: スライドと論文を並べた画面を別の窓に映し、手元には台本と根拠の一覧を出す
- **単語帳・数式帳と読解ノート**: 全論文の用語と数式を横断して引き、どこまで読めたかをノートに残す

全文の対訳は、PaperLens を MCP サーバーとして Claude Desktop や Claude Code に登録し、Claude に頼みます。翻訳用の API を別に契約する必要はありません。

## 2. 開発に至った背景

### 2-1. 研究室の輪講・抄読

僕の研究室では、輪講・抄読をやっています。担当者が論文や参考書を精読し、要点を絞って発表することで、参加者全体と効率よく知識を共有する場です。

流れはだいたいこんな感じです。

1. 担当の論文（または参考書の章）が割り当てられる
2. 担当者が英語の原文を精読する
3. 要点を日本語のスライドにまとめる
4. 輪講当日、スライドを使って発表する
5. 教授や参加者からの質問に答える

### 2-2. 輪講で起きていたこと

この流れの中で、発表者がつまずく場面がたびたびありました。

特に困ったのは、教授や参加者から **「スライドのこの部分は、論文のどこを根拠にしているの？」** と聞かれたときに、該当箇所を示せないことです。スライドを作るときには確かに論文を読んでいるのに、どの文をもとにまとめたのかが手元に残っていない。PDF をスクロールしながら探し始めることになります。

また、原文の英語がきちんと読めていないと、**日本語のスライドと原文の整合が取れない** こともありました。スライドにはこう書いてあるのに、原文を突き合わせると意味が少し違う、という状態です。

ほかにも、こんな場面はよくありました。

- 論文に出てくる英単語の意味や、その論文の中での使われ方を説明できない
- 論文内の文章を日本語に直せない
- 数式や単語の意味合いを質問されても答えられない

### 2-3. 課題を整理すると

| 輪講で起きること | これまで | PaperLens なら | 節 |
|---|---|---|---|
| スライドの根拠はどこ？ | PDF をスクロールして探す | スライドの囲みと論文の該当箇所が線でつながっている | 3-1 |
| 原文とスライドの整合 | 英語を読み直して突き合わせる | 1 文ごとの対訳で、原文と訳を並べて確かめる | 3-2 |
| 文章を日本語に直す | 自力では訳しきれないことがある | 対訳の訳を下書きに、自分で直した訳を残す | 3-2 |
| この単語の意味は？ | その場で辞書を引く | 用語の説明と「この論文での使われ方」を記録済み | 3-3 |
| この式の意味は？ | 答えられない | 数式を TeX に起こし、記号ごとの意味まで記録済み | 3-4 |

どの場面も、論文の文章・訳・単語や数式の解釈・スライドが、手元でひとまとまりになっていないと答えられません。そして答えられなければ、輪講の目的である参加者との知識共有も、そこで止まってしまいます。

だったら、それらの解釈も含めてひとつのアプリで管理できれば、一気に解決できるのでは？というのが出発点でした。

## 3. 課題ごとに、機能をどう効かせたか

2-1 の流れに当てはめると、スライド作り（手順 3）を支えるのが **根拠の対応**、精読（手順 2）を支えるのが **対訳・用語・数式**、発表と質疑（手順 4・5）を支えるのが **発表モード** です。ここからは、2 章の課題とのつながりを 1 つずつ書いていきます。

### 3-1. 「根拠はどこ？」に答える — 発表スライドと論文の対応

輪講でいちばん困っていた場面に効くのが、この機能です。左にスライド、右に論文を並べて、次の手順で根拠をつないでいきます。

1. スライドの一部をドラッグで囲むと、グループができる
2. グループを選んだまま、論文の文を選んで「文章としてリンク」を押すか、図・数式の範囲を囲む
3. グループと論文の該当箇所が、グループの色の線でつながる

1 つのグループから何か所にでもリンクできるので、「このまとめは Abstract と Method の両方を根拠にしている」といった対応もそのまま残せます（上の画像のオレンジの線がそれです）。片方が画面の外にあるときは点線で端まで引くので、スクロールしても対応を見失いません。

スライドは PDF でも PPTX でも取り込めます（PPTX は LibreOffice か Keynote で PDF に変換します）。対応関係は読解ノートの「発表スライドとの対応」にも書き出され、スライドを作り直して差し替えても、囲んだグループとリンクは残ります。

もちろん、根拠をつなぐのはスライド作りに一手間増えることでもあります。その手間を減らすために、この操作は MCP にも公開していて、Claude にスライドの文字から論文の該当文を探させ、リンクの下書きを作らせることもできます。

スライドを作るときに根拠をつないでおけば、発表で聞かれたときには**線をたどるだけ**で答えられます。

### 3-2. 原文とスライドの整合を取る — 1 文ごとの対訳

日本語のスライドと原文が噛み合わないのは、そもそも原文を 1 文ずつ正確に読めていないことが原因です。なので、論文を文単位に分けて、1 文ずつ訳を並べることにしました。

![論文の PDF と、右側に 1 文ずつの対訳カードが並ぶ画面](/projects/images/paperlens-translation.webp)
*中央に原文の PDF、右に 1 文ずつの対訳。マーカーを引いた箇所は PDF 上にも色が付く（この画像は GROBID を使わない簡易解析で分けたもの）*

PDF 上の文とサイドバーのカードは双方向に連動していて、PDF の文を押すとその訳のカードへ、カードを押すと PDF のその位置へ飛びます。キーボードだけで前後の文や未訳の文へ移れるので、精読のテンポが落ちません。

全文の訳は、MCP サーバーとして登録した Claude に頼みます。訳は画面にすぐ反映され、気になるところは手で直せます。手で直した訳には印が付き、あとから機械の訳で上書きされることはありません。

副次的な課題だった「論文内の文章を日本語に直せない」にも、この対訳がそのまま効きます。ただし、機械の訳はあくまで下書きです。原文と並べて確かめ、自分で直した訳を残すことを前提にしています。スライドに書いた日本語と、原文・訳を並べて見比べられるので、「スライドではこう言っているけど、原文は本当にそう書いてある？」を発表の前に自分で確かめられます。

### 3-3. 「この単語の意味は？」に答える — 用語と「この論文での使われ方」

論文の英単語は、辞書の意味だけでは足りません。同じ単語でも、分野や論文によって指すものが変わるからです。なので用語の記録には、1 文の説明・詳しい説明に加えて、**「この論文での使われ方」** の欄を設けました。

![用語タブ。用語ごとに 1 文の説明、詳しい説明、この論文での使われ方、関連する用語が並ぶ](/projects/images/paperlens-terms.webp)
*用語タブ。「この論文での使われ方」を残しておくと、聞かれても論文の文脈で答えられる*

PDF で語を選んで「用語を調べる」を押すと、Claude が説明の下書きを作ります（画面から Claude を呼ぶこの操作だけは API キーを設定して使います。キーが無くても手で入力できます）。用語の見出しを押すと、論文中でその語が出てきた場所に飛びます。

対訳の側には、訳語を決めておく用語集もあります。「global token」は「グローバルトークン」と訳す、と登録しておくと、Claude はそれ以降の訳でその訳語を使います（登録前の訳は自動では書き換えません）。スライドと訳で用語がぶれるのを防ぐためのものです。

### 3-4. 「この式は？」に答える — TeX と記号の意味

数式も、質問されて答えに詰まりやすいところでした。式の形は追えても、「この記号は何？」「なぜここで割るの？」と聞かれると止まってしまう。

PaperLens では、PDF で数式を選んで「数式にする」を押すと、選んだ範囲を TeX に書き起こし、式の役割と読み方、記号ごとの意味の一覧を残せます（これも API キーを設定したとき。手で書くこともできます）。記号には行列・ベクトル・スカラーといった種類も付けられます。

![数式タブ。式(1)が TeX からきれいに表示され、その下に説明と記号ごとの意味の一覧が並ぶ](/projects/images/paperlens-equations.webp)
*数式タブ。式を KaTeX で表示し、Q・K・V・d_k といった記号ごとに意味を残す*

式を押すと、論文中のその式の位置に飛びます。スライドの数式も 3-1 の「数式」リンクで論文の式とつないでおけば、スライドから論文の式へ飛び、数式タブで記号の意味を確かめる、という流れで答えられます。

### 3-5. 発表と質疑で答える — 発表モードと台本

ここまでの記録も、発表中に探す操作が増えては意味がありません。そこで、スライドと論文を並べた画面のまま発表できる **発表モード** を作りました。

- **発表の窓**: スライドと論文を並べた画面（線も含む）を別の窓に全画面で映す。デスクトップ版では外部ディスプレイに出る
- **手元の窓**: スライドの順に、左にそのスライドで話すこと（台本）、右にグループのメモとリンクした論文の箇所を出す

![発表モードの手元の窓。スライドごとに台本と、グループのメモ・リンクした論文の箇所が並ぶ](/projects/images/paperlens-presenter.webp)
*発表中の手元の画面。スライドごとの台本の横に、そのスライドの根拠の一覧が並ぶ*

台本でページやグループを押すと、発表の窓がそこへ動きます。質問されたら手元で該当グループを押すだけで、映している論文の側がその箇所へ移る、という使い方です。PPTX を取り込んだときは、発表者ノートが台本に入ります。

さらに発表の窓は、論文の横に **補足情報**（3-2〜3-4 の対訳・用語・数式）を出す面にも切り替えられます。「この単語の意味は？」「この式は？」と聞かれても、発表を止めずにその場で記録を開いて答えられる。ここで、ひとつのアプリにまとめた意味がいちばん出ると思っています。

### 3-6. 続けて読むために — 単語帳・数式帳と読解ノート

輪講は 1 回で終わりではなく、関連する論文を何本も読んでいきます。前に読んだ論文で調べた用語を、また一から調べ直すのはもったいない。なので、全論文の用語と数式を 1 つの画面に集めた **単語帳・数式帳** を用意しました。

![単語帳の画面。記録した用語と、対訳の用語集が 1 つのリストにまとまっている](/projects/images/paperlens-list.webp)
*単語帳。各論文で記録した用語と、対訳の用語集をまとめて引ける*

論文ごと・ページ順でも、五十音・ABC 順でも並べ替えられて、項目を押すとその論文の該当箇所に飛びます。五十音・ABC 順にすると、複数の論文で調べた同じ用語が 1 行にまとまり、**論文ごとの意味を並べて見比べられます**。3-3 の「この論文での使われ方」が、論文をまたいで効いてくるところです。

また、論文を取り込むとテンプレートから読解ノート（`note.md`）が作られます。テンプレートは「概要をつかむ → 精読する → 検討する → まとめる」の段階に分かれていて、途中で読むのをやめても、どこまで理解したかがノートを見れば分かります。論文一覧も読解の段階（未読・概要把握・精読・検討・まとめ済み）で絞り込めるので、担当論文を精読まで進めたかをひと目で確認できるのも地味に便利です。

## 4. 技術的な構成

### 4-1. 全体像

npm workspaces のモノレポで、画面・ローカルサーバー・MCP サーバーが同じロジック（`packages/core`）を共有しています。`packages/core` は外部依存ゼロにしました。

| 領域 | 使っているもの |
|---|---|
| 画面 | React 19 / TypeScript / Vite / pdf.js / KaTeX |
| サーバー | Node.js（`127.0.0.1` のみで待ち受け）/ SSE で保管庫の変更を通知 |
| 文分割 | GROBID（Docker）/ 無いときは pdf.js による簡易解析（ワーカースレッド） |
| AI 連携 | MCP サーバー（stdio）/ Anthropic SDK |
| デスクトップ | Electron |

画面はブラウザでもデスクトップ版（Electron）でも開けますが、中身は同じローカルサーバーと画面です。MCP サーバーは同じ処理を直接呼ぶので、アプリを起動していなくても Claude から操作できます。

### 4-2. なぜ「1 文ごと」が成立するのか — GROBID

1 文ごとの対訳の核は、GROBID という論文解析エンジンです。`segmentSentences=1` と `teiCoordinates=s` を付けて PDF を投げると、文単位で PDF 上の座標が付いた XML が返ってきます。

```xml
<s coords="1,53.80,194.57,238.71,9.29;1,53.80,205.00,238.71,9.29">
  We study sparse attention under long contexts.
</s>
```

この座標を pdf.js の描画に重ねると、原文の 1 文と画面の枠が 1 対 1 で対応します。2 段組・ハイフネーション・数式・脚注が混ざる論文で、自前のテキスト抽出だけでここまで正確に文を切るのはまず無理なので、ここは素直に専用のエンジンに任せると決めました。GROBID が無いときは、pdf.js による簡易解析に自動で切り替わります。

### 4-3. なぜ「ローカルで動く OSS」にしたか

研究室では、まだ公開されていない原稿を読む場面もあります。PDF を他人のサーバーに上げる SaaS 型だと、そうした原稿は扱えません。

| 形態 | 判定 | 理由 |
|---|---|---|
| SaaS（クローズド） | ✗ | 未公開の原稿を他人のサーバーに置くことになる |
| OSS + ホスト型 Web | ✗ | 結局 PDF がサーバーに上がる。運用費も誰かが負う |
| **OSS + ローカル実行** | **✓** | PDF が端末から出ない / pdf.js がそのまま使える |

なので、サーバーは `127.0.0.1` にしか bind せず、Host と Origin も確かめて、別のサイトからの操作も断ります。サーバーが勝手に本文を外へ送る経路は作っていません。外へ通信が出るのは、利用者が Claude に訳を頼んだとき、API キーで下書きを作ったとき、URL から論文を取り込んだときだけです。GROBID も既定では CrossRef に問い合わせに行くので、`consolidateHeader=0` で切って、未公開原稿のタイトルが外へ出ないようにしています。

副作用として、全文の翻訳を MCP 経由で Claude に任せる形にできたのは嬉しい誤算でした。SaaS なら、サーバー側で翻訳 API を叩いてその費用を誰かが払う必要があります。ローカル実行なら、普段使っている Claude にそのまま頼めて、翻訳専用の API や SaaS を別に挟まずに済みました。

### 4-4. データベースを持たない保管庫

データベースは使わず、保管庫フォルダの普通のファイルにすべてを置いています。

```
<保管庫>/
└── papers/<論文ID>/
    ├── paper.pdf               取り込んだ PDF
    ├── note.md                 読解ノート
    ├── paperlens.json          マーカー・用語・数式
    ├── sentences.json          1 文ずつの対訳
    ├── sentences.status.json   解析の進み具合
    ├── slides.pdf              発表スライド
    └── slides.json             スライドの囲みと論文へのリンク・台本
```

訳・用語・数式・スライドとの対応が、論文ごとに 1 つのフォルダにまとまります。「ひとつで管理する」を、ファイルの形でも実現しているわけです。

そのうえで、**アプリを捨ててもデータが読める** ことを優先しました。同じフォルダを Obsidian の保管庫としてそのまま開けるので、普段のノートと論文のメモが同じ場所に並びます。Obsidian でノートを書き換えても、PaperLens の画面にすぐ反映されます。

## 5. 設計思想

ここが一番時間をかけたところです。

### 5-1. 再解析しても訳が消えない

輪講の準備で積み上げた訳が、解析のやり直しで消えては困ります。

想定しているのは、最初は GROBID 無しの簡易解析で読み、あとから GROBID を入れて解析し直す、という使い方です。文の切れ目が変わっても訳が外れないように、構造データ（文の区切りと座標）と注釈（訳・メモ）を分けて保存し、原文を正規化したハッシュで結び直すようにしました。行末で割れた `block-` + `sparse` と、GROBID が返す `block-sparse` を同じハッシュにするために、正規化で文字間のハイフンを落としています。ここを作り込まないと「GROBID を入れたら訳が全部外れた」が起きます。

### 5-2. 人が考えた跡を、機械が消さない

画面で読みながら、裏では Claude が MCP 経由で訳を書き込んでいく、という使い方になります。2 つのプロセスが同じ論文を触るので、雑に作ると片方の変更が消えます。

- マーカー・用語・数式やスライドの対応は丸ごと上書きせず、「追加・更新・削除」の操作として、書く直前に読み直した最新の状態に当てる
- 人が手で直した訳には印を付けて、機械の訳で上書きしない

自分で練った訳が Claude に上書きされてしまったら目も当てられません。輪講の準備に使う以上、ここは特に大事にしました。ただ、対訳のファイルだけはプロセスをまたぐ排他まではしていないので、画面と Claude が同じ論文の対訳をまったく同時に書き換えると、片方の変更が消えることがあります。これは既知の制約として README に書いています。

### 5-3. 「黙って壊れない」

個人的に、ここは特に譲れなかったところです。

GROBID が無いときの簡易解析では、2 段組の左右が語単位で混ざったり、数式を含む段落が丸ごと抜け落ちたりすることがあります。怖いのは後者で、残った断片が文法の通る英文にくっついてしまうと、Claude はそれをもっともらしい日本語に訳します。読む側には「論文がそう書いてある」としか見えません。

そのまま輪講で発表してしまったら、まさに「スライドと原文が噛み合わない」状態を、道具のほうが作ってしまうことになります。「もっともらしい訳が付いているのに、原文が欠けている」状態がいちばん危ない。そう考えて、読み順の崩れと本文の欠落をそれぞれ自動で検出し、画面のバッジと MCP の両方で知らせるようにしました。警告が出ないから壊れていない、とまでは言えませんが、少なくとも「壊れているのに黙っている」状態は無くせました。

### 5-4. 品質を数字で確かめる

5-3 の対策が本当に効いているかを確かめるために、簡易解析の精度を `npm run measure` で測っています。正解が分かっている論文風の PDF と、LaTeX で組んだ検証用の論文を通して、本文の再現率と混入数を出すスクリプトです。

実はこの計測器は 2 回作り直しています。

- 合成 PDF だけを測っていた頃は、実物の壊れ方を 1 つも再現できないまま「全シナリオ 100%」と表示していた
- LaTeX で組んだ論文を足したあとも、その中身から数式が抜けていた。数式の多い論文は技術的な段落のほぼ全行にギリシャ文字が入るので、**壊れる原因を取り除いた標本で 100% を出していた**

いまは数式の濃い版や和文の論文も含めて、合成 PDF 15 本と、LaTeX で組んだ検証用の論文 14 本のすべてで、再現率 100%・混入 0 件を確認しています。「測っているつもりで測れていなかった」のは、このプロジェクトで一番反省したところでした。

## 6. 開発プロセスの工夫 — 「動く」と「壊れない」の間を埋める

### 6-1. 2 つのアプリをひとつにまとめ直した

PaperLens は、最初から今の形だったわけではありません。

| 時期 | 出来事 |
|---|---|
| 2026-09-05 | 1 文単位の対訳リーダー「LogiXiv」の初期実装 |
| 2026-09-14 〜 15 | 批評サイクルで解析・保存・UI・MCP の不具合をまとめて修正 |
| 2026-10-12 | 読解ノートアプリ「PaperLens」の最初の版を、同じリポジトリに作る |
| 2026-10-13 | PaperLens に LogiXiv の 1 文対訳を取り込み、単語帳・数式帳を載せる |
| 2026-10-17 | 発表スライドを論文の隣に並べ、線でつなぐ機能を追加 |
| 2026-10-24 〜 27 | 発表モード（別の窓に映す）を作り、台本と補足情報を足す |

最初の LogiXiv は「1 文ごとの対訳を作って共有する」道具でした。次に作った PaperLens は、読解の記録に必要なのは自分が引っかかった箇所だけだと考えて、あえて全文の対訳をやめ、読解ノートに絞った道具として始めています。ところが翌日には、LogiXiv の 1 文対訳を取り込み直していました。対訳とノートを別々の道具で行き来するのは、2 章で書いた「解釈がひとまとまりになっていない」状態を、自分の道具で再現しているようなものだったからです。

結果的に、論文を「文」の単位で精読する土台が先にできあがり、輪講でいちばん困っていた根拠の対応と発表モードを、その上に載せる形になりました。

### 6-2. 批評サイクルを回す

開発の大半は Claude Code と一緒に進めました。ただ「書いてもらって終わり」にすると、動いているように見えて実害のある不具合が残ります。

なので、ある程度機能がそろうたびに **「批評サイクル」** を回しました。わざと壊れた PDF や意地の悪い入力を投げる敵対的なテストをして、見つかった問題をまとめて直す、という流れです。1 回目のサイクルでは、たとえばこんなものが見つかりました。

- 略語判定が部分一致になっていて、`test.` や `systems.` で文が切れなくなっていた
- 900 ページの PDF を 1 本読むと、サーバーのイベントループが 68 秒止まっていた → pdf.js をワーカースレッドへ
- 開いているだけで SSE の通知が多すぎて、Claude の書き込みが 6 倍遅くなっていた → 300ms で通知を合体

「動く」と「壊れない」の間にはかなり距離がある、というのを身をもって知りました。

### 7-2. 速さのために Go へ移すか、検討してやめた話

論文が増えたときの集計の速さが気になったので、ロジックを Go に移す案を実測して比べました（実データ 3 本を複製した、論文 300 本の合成データで計測）。結論は **移さない** です。

| 実装（論文 300 本の単語帳集計） | 時間 |
|---|---|
| 現状の TypeScript | 1.0〜1.3 秒 |
| Go（8 goroutine） | 0.15〜0.35 秒 |
| TypeScript ＋ 更新時刻でのキャッシュ（2 回目以降） | **8〜14 ミリ秒** |

遅さの原因は言語ではなく、用語集を取り出すためだけに毎回すべての対訳ファイルを読み直して解析する作りのほうでした。Go に移しても数倍ですが、キャッシュなら数十〜百倍速くなります。さらに、論文の取り込みで時間の大半を占める PDF の処理は pdf.js が担っていて、Go には同じ座標を出すライブラリが無い。差し替えると既存の文のハッシュがずれてしまいます。

実際に作りを直した結果、単語帳・数式帳の読み込みは 1,112 ミリ秒から 86 ミリ秒になりました。「速い言語に移す」より「作りを直す」ほうが効く、というのを数字で確かめられたのは良い経験でした。

## 8. さいごに

最初のコミットから 2 ヶ月。116 コミット、25 PR で、輪講に持っていける形になってきました。

「スライドのここ、論文のどこ？」と聞かれて答えられない、という研究室でよく見るあの場面をなんとかしたかっただけだったのですが、結果として GROBID・pdf.js・MCP・Electron まで触ることになりました。

作りながら分かったのは、輪講で詰まる場面の多くが、論文の文章・訳・解釈・スライドが別々の場所にあることから来ていた、ということです。スライドと論文の根拠が離れているから線でつなぐ。原文と日本語が離れているから 1 文ずつ並べる。単語や数式と、その論文での意味が離れているから一緒に残す。そして、それらを発表の場でひとつの画面から引けるようにする。加えて、機械の訳が原文の欠落を隠さないことも、根拠を扱う道具には欠かせないと分かりました。これが、2 ヶ月で得た一番大きな収穫だったと思います。

いまはまだ発表者の手元の道具ですが、輪講の目的は参加者との知識共有なので、いずれは聞く側にも役立つ形にしていきたいところです。ここまで読んでくださってありがとうございました。
