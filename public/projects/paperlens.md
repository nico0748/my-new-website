
# 論文リーダー「PaperLens」をつくってみた話

英語の論文を読むたびに、PDF と翻訳ツールとメモ帳を行ったり来たりするのに疲れて作り始めたアプリです。2 か月ほど触り続けて、別々に作っていた 2 つのアプリを 1 つにまとめ直すところまで来たので、設計で考えたことを残しておきます。

## 1. システム概要

「PaperLens」は、論文 PDF を **1 文ごとの対訳** で読みながら、訳・用語・数式・読解メモを **Markdown の保管庫（vault）** に残していく、ローカルファーストな論文リーダーです。

画面の中央に原文の PDF、右のサイドバーに 1 文ずつの日本語訳が並びます。PDF 上の文とサイドバーのカードは双方向に連動していて、PDF の文を押すとその訳へ、訳を押すと PDF のその位置へ飛びます。全文の翻訳は **Claude を MCP 経由で呼び出す** ので、翻訳 API のキーも追加の費用もかかりません。

もともとは「1 文単位の対訳リーダー（LogiXiv）」と「読解ノートアプリ（旧 PaperLens）」を別々に作っていたのですが、結局どちらも同じ論文を開いて使っていたので、1 つのアプリに統合しました。

## 2. 作り始めた背景

### 2-1. 論文を読むときの現状フロー

僕が英語の論文を読むときは、だいたいこんな流れでした。

1. PDF をビューアで開く
2. 分からない文をコピーして翻訳サイトに貼る
3. 改行やハイフンで文が崩れるので、手で直してからもう一度貼る
4. 出てきた用語や数式を、別のメモアプリに書き写す
5. 数日後、「あの用語どの論文に出てきたっけ」となって探し回る

訳した文と原文の位置が結び付いていないので、あとから読み返すと「この訳はどこの文のものか」が分からない。用語や数式のメモも論文ごとに散らばっていて、横断して引けない。ここをなんとかしたい、というのが出発点でした。

### 2-2. 既存のやり方の限界

| 困りごと | これまで | PaperLens なら |
|---|---|---|
| 訳と原文の対応 | コピペした時点で切れる | 1 文ごとに PDF 上の位置と結び付いている |
| 2 段組・行末ハイフン | 貼る前に手で直す | 解析側で文単位に組み直す |
| 用語・数式の記録 | 論文ごとにバラバラのメモ | 全論文を横断する単語帳・数式帳 |
| 翻訳の費用 | API キーや有料プラン | Claude を MCP 経由で使うので追加費用なし |
| データの持ち主 | サービス側 | 手元のフォルダの普通のファイル |

## 3. 技術的な構成

### 3-1. 全体像

npm workspaces のモノレポで、画面・ローカルサーバー・MCP サーバーが同じロジック（`packages/core`）を共有しています。`packages/core` は外部依存ゼロにしました。

| 領域 | 使っているもの |
|---|---|
| 画面 | React 19 / TypeScript / Vite / pdf.js / KaTeX |
| サーバー | Node.js（`127.0.0.1` のみで待ち受け）/ SSE で保管庫の変更を通知 |
| 文分割 | GROBID（Docker）/ 無いときは pdf.js による簡易解析（ワーカースレッド） |
| AI 連携 | MCP サーバー（stdio）/ Anthropic SDK |
| デスクトップ | Electron |

### 3-2. なぜ「1 文ごと」が成立するのか — GROBID

このアプリの核は、GROBID という論文解析エンジンです。`segmentSentences=1` と `teiCoordinates=s` を付けて PDF を投げると、**文単位で PDF 上の座標が付いた XML** が返ってきます。

```xml
<s coords="1,53.80,194.57,238.71,9.29;1,53.80,205.00,238.71,9.29">
  We study sparse attention under long contexts.
</s>
```

この座標を pdf.js の描画に重ねると、原文の 1 文と画面の枠が 1 対 1 で対応します。2 段組・ハイフネーション・数式・脚注が混ざる論文で、自前のテキスト抽出だけでここまで正確に文を切るのはまず無理なので、**ここは素直に専用のエンジンに任せる**と決めました。

### 3-3. なぜ「ローカルで動く OSS」にしたか

研究室や企業で読む論文には、まだ公開されていない原稿も含まれます。PDF を他人のサーバーに上げる SaaS 型だと、そもそも使ってもらえません。

| 形態 | 判定 | 理由 |
|---|---|---|
| SaaS（クローズド） | ✗ | 未公開論文を他人のサーバーに置く設計は通らない |
| OSS + ホスト型 Web | ✗ | 結局 PDF がサーバーに上がる。運用費も誰かが負う |
| **OSS + ローカル実行** | **✓** | PDF が端末から出ない / pdf.js がそのまま使える |

そこで、サーバーは `127.0.0.1` にしか bind せず、**本文が端末の外に出る経路をコードから消しました**。Host と Origin も確かめて、別のサイトからの操作も断ります。GROBID も既定では CrossRef に問い合わせに行くので、`consolidateHeader=0` で切って未公開原稿のタイトルが外へ出ないようにしています。

副作用として、翻訳を Claude の MCP 経由にできたのが大きかったです。SaaS ならサーバー側で翻訳 API を叩いて、その費用を誰かが払い、本文が第三者の翻訳エンジンを通る。ローカル実行ならその全部が消えます。「プライバシーのためにローカルにした」結果、「翻訳コストもゼロになった」という、狙っていなかった嬉しさでした。

### 3-4. データベースを持たない保管庫

データベースは使わず、保管庫フォルダの普通のファイルにすべてを置いています。

```
<保管庫>/
└── papers/<論文ID>/
    ├── paper.pdf               取り込んだ PDF
    ├── note.md                 読解ノート
    ├── paperlens.json          マーカー・用語・数式
    ├── sentences.json          1 文ずつの対訳
    └── sentences.status.json   解析の進み具合
```

**アプリを捨ててもデータが読める** ことを最優先にしました。同じフォルダを Obsidian の保管庫としてそのまま開けるので、普段のノートと論文のメモが同じ場所に並びます。

## 4. 設計思想

ここが一番時間をかけたところです。

### 4-1. 再解析しても訳が消えない

最初は GROBID 無しの簡易解析で読み、あとから GROBID を入れて解析し直す、という使い方を想定しています。このとき、文の切れ目が変わっても、それまでに付けた訳が外れては困ります。

そこで、構造データ（文の区切りと座標）と注釈（訳・メモ）を分けて保存し、**原文を正規化したハッシュで結び直す** ようにしました。行末で割れた `block-` + `sparse` と、GROBID が返す `block-sparse` を同じハッシュにするために、正規化で文字間のハイフンを落としています。ここを作り込まないと「GROBID を入れたら訳が全部外れた」が起きます。

### 4-2. 人と Claude が同時に書いても壊れない

画面で読みながら、裏では Claude が MCP 経由で訳を書き込んでいく、という使い方になります。2 つのプロセスが同じファイルを触るので、丸ごと上書きすると片方の変更が消えます。

- 注釈は丸ごと上書きせず、「追加・更新・削除」の **操作** として、書く直前に読み直した最新の状態に当てる
- 人が手で直した訳には印を付けて、**機械の訳で上書きしない**
- 訳は「正解が 1 つ」、メモは「多いほど良い」なので、マージの規則をあえて非対称にした

### 4-3. 「黙って壊れない」

個人的に一番大事だと思っているのがここです。

GROBID が無いときの簡易解析では、2 段組の左右が語単位で混ざったり、数式を含む段落が丸ごと抜け落ちたりすることがあります。怖いのは後者で、残った断片が文法の通る英文にくっついてしまうと、Claude はそれをもっともらしい日本語に訳します。読む側には「論文がそう書いてある」としか見えません。

**「もっともらしい訳が付いているのに、原文が欠けている」状態が一番危ない** と考えて、読み順の崩れと本文の欠落をそれぞれ自動で検出し、画面のバッジと MCP の両方で申告するようにしました。検出できないことは「壊れていない保証」ではありませんが、少なくとも「壊れているのに黙っている」状態は無くせました。

### 4-4. 品質を数字で確かめる

解析の精度は `npm run measure` で測っています。正解が分かっている論文風の PDF と、LaTeX で組んだ実物の論文を通して、本文の再現率と混入数を出すスクリプトです。

実はこの計測器は 2 回作り直しています。

- 合成 PDF だけを測っていた頃は、実物の壊れ方を 1 つも再現できないまま「全シナリオ 100%」と表示していた
- 実物の論文を足したあとも、その中身から数式が抜けていた。数式の多い論文は技術的な段落のほぼ全行にギリシャ文字が入るので、**壊れる原因を取り除いた標本で 100% を出していた**

いまは数式の濃い版と和文の論文も含めて、2 段組で再現率 100%・混入 0 件を確認しています。「測っているつもりで測れていなかった」のは、このプロジェクトで一番反省したところでした。

## 5. 開発プロセスの工夫 — 批評サイクルを回す

開発の大半は Claude Code と一緒に進めました。ただ「書いてもらって終わり」にすると、動いているように見えて実害のある不具合が残ります。

そこで、ある程度機能がそろうたびに **「批評サイクル」** を回しました。わざと壊れた PDF や意地の悪い入力を投げる敵対的なテストをして、見つかった問題をまとめて直す、という流れです。初期実装から 10 日後の 1 回目のサイクルでは、たとえばこんなものが見つかりました。

- 略語判定が部分一致になっていて、`test.` や `systems.` で文が切れなくなっていた
- 900 ページの PDF を 1 本読むと、サーバーのイベントループが 68 秒止まっていた → pdf.js をワーカースレッドへ
- 開いているだけで SSE の通知が多すぎて、Claude の書き込みが 6 倍遅くなっていた → 300ms で通知を合体

「動く」と「壊れない」の間にはかなり距離がある、というのを身をもって知りました。

### 6-2. 速さのために Go へ移すか、検討してやめた話

論文が増えると単語帳の集計が遅くなってきたので、ロジックを Go に移す案を実測して比べました。結論は **移さない** です。

| 実装（論文 300 本の単語帳集計） | 時間 |
|---|---|
| 現状の TypeScript | 1.0〜1.3 秒 |
| Go（8 goroutine） | 0.15〜0.35 秒 |
| TypeScript ＋ 更新時刻でのキャッシュ | **8〜14 ミリ秒** |

遅さの原因は言語ではなく、「毎回すべてのファイルを読み直して解析し直す作り」のほうでした。さらに、時間の大半を占める PDF の処理は pdf.js が担っていて、Go に同じ座標を出すライブラリが無い。差し替えると既存の文のハッシュがずれてしまいます。「速い言語に移す」より「作りを直す」ほうが 100 倍効く、というのを数字で確かめられたのは良い経験でした。

## 7. さいごに

「論文を読むたびにコピペするのが面倒」というだけで始めたアプリでしたが、結果として GROBID・pdf.js・MCP・Electron まで触ることになりました。

一番の収穫は、**「何を守りたいか」から設計を決めると、選択が自然に決まっていく** ということでした。未公開の原稿を守りたいからローカル実行、ローカル実行だから翻訳は MCP 経由、データを守りたいから DB を持たずに普通のファイル、読む人を守りたいから「黙って壊れない」。
